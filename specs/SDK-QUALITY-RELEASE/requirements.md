# SDK-QUALITY-RELEASE requirements

Every requirement this specification owns, with the proof that closes it. Delivery state and
public evidence for each ID are recorded in [`status.json`](status.json); this file defines what
each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md), the test contract
in [`test-spec.md`](test-spec.md), and the work order in [`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `SDK-QUALITY-RELEASE-R001` | **SDK release builds against a published compatible graph-client wheel.** The SDK release pipeline builds and publishes an installed wheel verified against a published, version-compatible graph-client wheel, confirming generated-type and native-kernel compatibility in an isolated installed consumer rather than a source overlay. | A release job that installs the published wheel in an isolated environment and verifies generated-type and kernel compatibility against the graph-client release. |
| `SDK-QUALITY-RELEASE-R002` | **Public-documentation scanner catches private addresses and hosts.** A documentation privacy scanner checks every public Markdown page for private IP ranges, host aliases, and environment-only domains, matching the strength of the graph service's own documentation privacy test and failing the build when a violation is present. | A planted-violation test that inserts a private IP address and an environment-only hostname into a documentation file and asserts the scanner fails, then confirms a clean tree passes. |
| `SDK-QUALITY-RELEASE-R003` | **Release workflow builds with the pinned managed Python, not the system one.** The release workflow installs and builds the SDK using the pinned Python toolchain declared in pyproject.toml rather than falling back to the hosting runner's system Python, while generated contracts and configuration, hardened serving, repository transport, and durable write-back remain intact and the public documentation site continues to build successfully. | A continuous-integration run of the release workflow asserting the build executes under the pinned interpreter and that the documentation site publishes successfully. |
| `SDK-QUALITY-RELEASE-R004` | **Public documentation follows a task-first README and site structure.** The public README follows a fixed section order leading with a one-file connector quick start, and the published documentation site presents a task-first tutorial and architecture guide. | A documentation build and link check in continuous integration confirming the README section order, that the one-file quick start example runs, and that the tutorial and architecture pages build without broken links. |
| `SDK-QUALITY-RELEASE-R005` | **Hosted CI reproduces the exact pinned dependency import locally.** Running the pinned install command locally reproduces the exact same dependency import graph used by hosted continuous integration, so a contributor's local verification matches the hosted release check without drifting from the top-level README's existing guidance. | A reproducibility test comparing the locally resolved import graph under the pinned install command against the hosted CI run's recorded result. |
